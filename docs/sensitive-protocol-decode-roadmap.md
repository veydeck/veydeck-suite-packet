# 敏感协议深度解码后续发展蓝图

## 背景

敏感协议深度解码的目标不是替代 Wireshark 的完整协议栈，而是在项目核心工作流中提供更直接的安全分析视角：识别敏感协议、提取关键字段、标记风险线索，并把结果稳定地展示在包详情、会话流、文件提取和数据包构造等功能中。

当前 MVP 已覆盖轻量级协议识别与字段提取，主要面向 TLS/SSL、SSH、FTP、MQTT、HTTP/2 等协议的初步解码。后续应优先补齐流重组、对象提取、风险标记和协议覆盖深度。

## 设计原则

- 保持解码结果可解释：优先展示原始字段、派生字段和置信度，避免黑盒结论。
- 不做透明解密承诺：TLS 等加密协议默认只能解析握手、证书、ALPN、SNI 等明文字段。
- 以会话为主要分析单位：单帧解码只能作为入口，完整判断需要依赖 TCP/UDP 会话重组。
- 解码器应可独立测试：每个协议解码器用字节样本覆盖正常、截断、异常和误判场景。
- 后端输出稳定结构：前端只负责展示，不在 UI 中重复实现协议解析逻辑。

## 当前 MVP 能力

- 包列表协议识别：在基础 TCP/UDP/HTTP/DNS/ICMP/ARP 之外，识别 TLS、SSH、FTP、MQTT、HTTP/2。
- 包详情深度解码：展示敏感协议的关键字段。
- TLS/SSL：解析记录类型、版本、握手类型、ClientHello SNI、ALPN、支持版本、证书数量和首证书摘要。
- SSH：解析 banner、协议版本和软件标识。
- FTP：解析命令和响应，隐藏 PASS 参数。
- MQTT：解析固定报头、CONNECT 和 PUBLISH 的基础字段。
- HTTP/2：识别连接前言和基础帧头。
- 前端：协议筛选下拉列表支持敏感协议，包详情中的深度解码区域默认折叠。

## 阶段 1：单帧深度解码增强

目标：在不引入复杂流重组的前提下，提高现有敏感协议的字段覆盖和误判控制。

建议任务：

- TLS：
  - 增加 cipher suite 名称映射。
  - 增加 extension 名称映射。
  - 提取 JA3/JA3S 指纹所需字段。
  - 识别 TLS Alert 等异常信号。
- SSH：
  - 增加常见软件版本风险提示。
  - 识别 banner 格式异常和弱版本。
- FTP：
  - 增加 USER、PASS、RETR、STOR、PORT、PASV 等命令分类。
  - 标记明文凭据风险。
- MQTT：
  - 增加 QoS、retain、dup 标志解析。
  - 解析 CONNECT flags 中的 username/password/will 标志。
- HTTP/2：
  - 增加 SETTINGS、HEADERS、DATA、GOAWAY 等帧类型字段展示。
  - 对截断帧和长度异常提供 warning。

交付标准：

- 每个协议至少覆盖 3 类典型样本：正常、截断、易误判。
- 包详情中的深度解码结果包含协议、标题、字段和可选 warnings。
- 包列表协议识别误判率不能明显影响常用协议筛选。

## 阶段 2：会话级重组与解码

目标：从“单包字段展示”升级为“会话上下文分析”，解决跨 TCP 分段、重传、乱序导致的解析不完整问题。

建议任务：

- 建立会话级 payload 重组服务：
  - TCP 按四元组和方向重组。
  - 处理重传、乱序、重复片段和 FIN/RST。
  - UDP 按会话聚合，但不强行拼接不连续载荷。
- 为深度解码增加会话入口：
  - 包详情仍展示单帧结果。
  - 追踪会话流展示会话级解码摘要。
  - 后续对象提取基于会话级数据。
- 增加解码置信度：
  - port-based hint。
  - payload magic/preface。
  - protocol state validation。

交付标准：

- HTTP/TLS/FTP/MQTT 至少支持常见跨帧载荷解析。
- TCP 重传不应导致重复解析出多个应用层对象。
- 会话流方向必须与客户端/服务端端点一致。

## 阶段 3：HTTP 对象提取 MVP

目标：自动检测 HTTP 流量中的传输对象，提供可下载文件。

建议任务：

- 支持 HTTP/1.x 响应对象提取：
  - Content-Type。
  - Content-Length。
  - Transfer-Encoding: chunked。
  - Content-Disposition 文件名。
  - gzip/deflate 解压选项。
- 生成对象元数据：
  - 文件名。
  - MIME 类型。
  - 字节大小。
  - SHA256。
  - 来源 pcap、会话、请求 URL、响应状态码。
- 提供下载接口：
  - 单文件下载。
  - 后续可扩展批量导出。
- 前端对象列表：
  - 按 pcap 展示提取文件。
  - 支持类型、大小、来源会话筛选。

交付标准：

- 能从常见 HTTP 图片、文本、二进制响应中提取文件。
- chunked 响应可以正确还原。
- 提取对象和原始会话可互相跳转定位。

## 阶段 4：更多敏感协议覆盖

目标：扩展到企业内网和攻防演练中常见的敏感协议。

优先级建议：

- SMB：
  - 识别 SMB 版本。
  - 展示命令类型、Tree Connect、Session Setup。
  - 后续分析 NTLMSSP、文件读写操作。
- RDP：
  - 识别连接协商。
  - 展示协议版本和安全层信息。
- LDAP：
  - 解析 bind/search 基础字段。
  - 标记明文 bind 风险。
- Kerberos：
  - 识别 AS-REQ、AS-REP、TGS-REQ、TGS-REP。
  - 后续提取可用于安全分析的票据元数据。
- SMTP/POP3/IMAP：
  - 解析明文认证、附件传输和服务器 banner。

交付标准：

- 新协议先提供识别和关键字段，不追求完整协议实现。
- 每个协议必须有测试样本和误判样本。
- 高风险字段需要脱敏或明确标注。

## 阶段 5：风险检测与分析视图

目标：把深度解码结果转化为更直接的安全分析线索。

建议任务：

- 风险标签：
  - 明文认证。
  - 弱 TLS 版本。
  - 可疑证书。
  - 敏感文件传输。
  - 异常协议字段。
- 统计视图：
  - 敏感协议分布。
  - 明文凭据事件。
  - 文件提取数量和类型分布。
  - 高风险会话列表。
- 检索能力：
  - 按协议字段搜索。
  - 按 SNI、证书摘要、SSH banner、FTP 用户名、MQTT topic 搜索。

交付标准：

- 风险标签来源可追溯到具体包或会话。
- 每条风险结果能跳转到包详情或会话流。
- 风险规则应可单测，避免 UI 侧硬编码判断。

## 后端模型建议

短期可以继续使用 `protocol_insights` 作为包详情响应字段。进入会话级和对象提取后，建议拆分为更稳定的结构：

- `ProtocolInsight`：单包或会话的解码结果。
- `ProtocolField`：字段名、字段值、字段类型、是否敏感。
- `ProtocolWarning`：解码异常、截断、明文凭据、弱配置等。
- `ExtractedObject`：提取文件的元数据和下载句柄。
- `SessionDecodeSummary`：会话级协议、端点、方向、对象、风险摘要。

## 测试策略

- 单元测试：
  - 每个 decoder 使用纯 bytes 样本。
  - 覆盖截断载荷、非目标协议、边界长度。
- 集成测试：
  - 使用 Scapy 构造 TCP/UDP 包并验证包详情输出。
  - 验证协议筛选值与解析结果一致。
- 回归测试：
  - TCP 重传不重复生成 HTTP/对象结果。
  - TCP/UDP 相同端点不会互相污染会话。
  - 明文密码字段必须脱敏。
- 样本管理：
  - 优先使用代码构造的小样本。
  - 大型 pcap 样本应放入独立目录，并避免提交敏感真实流量。

## 风险与边界

- TLS 加密内容无法在无密钥情况下解密，产品文案应避免暗示可读取加密后的应用数据。
- HTTP/2 HEADERS 需要 HPACK 解码，建议引入成熟库或独立实现并充分测试。
- SMB、Kerberos 等协议复杂度高，应分阶段提取元数据，避免一次性实现完整解析器。
- 文件提取涉及磁盘写入和下载接口，需要做路径隔离、大小限制和 MIME 校验。
- 敏感字段展示需要默认脱敏，并提供明确的用户操作入口查看原始内容。

## 推荐下一步

优先进入阶段 2 的 TCP 会话重组能力。它是 HTTP 对象提取、HTTP/2 多帧解析、FTP 数据连接关联和后续风险检测的基础。没有稳定重组层，深度解码容易停留在单帧字段展示，后续功能会反复遇到分段、重传和方向判断问题。
